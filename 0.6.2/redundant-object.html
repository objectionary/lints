Redundant object

If a named object gets used a single time, it counts as “redundant” and should be inlined.

Incorrect:

# Foo.

[] > foo
  [] >> bar
    52 > spb
    spb.plus 2 > @

Correct:

# Foo.

[] > foo
  [] >> bar
    52.plus 2 > @

The lint also skips an object declared outside a formation with void attributes when its single reference occurs inside that formation. For example, a mapper may read a value from its enclosing scope for each item. Inlining the value into the mapper would rebuild it for every application. A reference within the declaration’s own formation does not cross that boundary.

An object referenced a single time is not redundant when that lone reference sits inside a recursive formation. Syntactically the name is mentioned once, but at runtime each step of the recursion evaluates it anew, and the named attribute lets all those evaluations share a single node. Inlining it would give every level of the recursion its own copy of the subgraph, so the lint skips such objects:

# Series.

[point] > series
  point.times point > squared
  poly 30 > @
  [n] > poly
    if. > @
      n.eq 0
      0
      ^.squared.plus (^.poly (n.minus 1))

A $-alias is also not redundant when its single reference reaches it from inside a nested formation. There, $ refers to the nested formation itself, not to the object where the alias was declared. Inlining the alias into that reference would change what it points to:

# Jeff.

[] > jeff
  $ > self
  [] > say-hello
    stdout ^.self > @

An object that is never referenced in the program is not reported either, since there is nowhere to inline it. Such an object may be a part of the interface of its formation, read by other programs, which the lint can’t see:

# A point at three and four.

[] > point
  3 > x
  4 > y

An attribute of the top object is not reported either, even if its own file reads it a single time, often in its own test. Such an attribute is a part of the public interface of the object, and other programs may read it. Only an attribute bound with >> is private and may be inlined:

# Flags of the open system call.

[] > flags
  64 > create
  8 > append

  (flags.create.plus flags.append).eq 72 ++> combines-flags

The same holds for an attribute of a nested formation, when that formation and every formation around it, up to the top object, are named, are not bound with >>, and are not tests. Other programs read net.address.padding just as they read net.address, so padding is not reported:

# The C structure of an address.

[] > net
  [host] > address
    00-00-00-00 > padding
    host.size.plus padding.size > size

Once any formation on that path is bound with >>, or is anonymous, its attributes are private again and may be inlined.

An attribute of a nested formation is not reported either, when its name is read through an object that is not a formation, such as c.empty below. The lint can’t tell which formation c stands for, so it assumes the reference may read any attribute named empty, unless it is bound with >>:

# A cell that knows whether it holds zero.

[] > app
  [x] >> cell
    x.eq 0 > empty
    empty.if > shown
      "zero"
      "other"
  cell 0 > c
  c.empty.if > @
    c.shown
    "?"
